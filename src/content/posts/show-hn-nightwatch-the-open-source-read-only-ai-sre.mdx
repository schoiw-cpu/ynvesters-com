It's 2:47 AM and your phone is screaming. You stare at a wall of metrics, logs scattered across four different dashboards, and a Slack thread that's already 40 messages deep — none of which actually explain *why* the service is degraded. You've been in this exact spot before: drowning in signal, starved of insight, with nobody to rubber-duck the problem at 3 AM except yourself.

That's the gap [Nightwatch](https://github.com/ninoxAI/nightwatch) is designed to fill. It's an open-source, read-only AI Site Reliability Engineering (SRE) agent that connects to your existing observability stack, watches for anomalies, and produces plain-language incident analyses — without touching a single production resource. No automated remediations that could make things worse. No scary write permissions. Just a tireless second brain that reads everything and explains what it sees.

---

## What Makes Nightwatch Different

Before you set anything up, it's worth understanding the design philosophy, because it shapes every configuration decision you'll make.

Most AI-in-ops tools today are sprinting toward autonomous remediation — they want to auto-scale your pods, restart your services, roll back your deployments. That ambition is real, but so is the risk. A misconfigured autonomous agent executing remediations during a complex, cascading failure can turn a P2 incident into a P1 catastrophe in seconds.

Nightwatch takes a deliberate step back. It is **read-only by design**. Every integration it ships with — Prometheus, Loki, Kubernetes, Datadog — is scoped to read/query access only. The agent never executes shell commands, never calls mutating API endpoints, and never opens pull requests. What it *does* do is ingest your telemetry, run it through an LLM-powered reasoning chain, and hand you a structured incident report you can act on.

This makes it a genuinely safe tool to deploy in regulated environments, cautious organizations, or any team that has been burned by automation gone wrong. Think of it as a very smart, very alert on-call engineer who has read-only access to your systems and will always tell you what they think — but always leaves the actual decisions to you.

## Prerequisites

Before starting, make sure you have:

- **Docker** and **Docker Compose** installed (v20+ recommended)
- An **OpenAI API key** (or a compatible local LLM endpoint — more on this below)
- At least one supported data source: Prometheus, Loki, Datadog, or a Kubernetes cluster with read-only kubeconfig
- Basic familiarity with YAML configuration files
- Git installed locally

Nightwatch is a Python-based application. If you prefer running it outside Docker, Python 3.11+ is required.

---

## Step 1: Clone the Repository

Start by pulling the project from GitHub:

```bash
git clone https://github.com/ninoxAI/nightwatch.git
cd nightwatch
```

Take a moment to look at the directory structure. The key folders you'll interact with are:

- `config/` — where your data source and LLM configuration lives
- `integrations/` — individual connector modules for Prometheus, Loki, Kubernetes, etc.
- `agents/` — the LLM reasoning chain logic
- `docker-compose.yml` — the quickest path to a running instance

---

## Step 2: Configure Your Environment Variables

Copy the example environment file:

```bash
cp .env.example .env
```

Open `.env` in your editor. The critical fields to fill in immediately:

```env
# LLM Provider
OPENAI_API_KEY=sk-your-key-here
LLM_MODEL=gpt-4o

# Or, if using a local model via Ollama or LiteLLM:
# LLM_BASE_URL=http://localhost:11434/v1
# LLM_MODEL=llama3

# Nightwatch runtime
NIGHTWATCH_ENV=production
LOG_LEVEL=INFO
```

**A note on model choice:** Nightwatch works best with a model that handles long context well, because incident analysis often means reasoning over thousands of log lines simultaneously. GPT-4o is the recommended default. If you're evaluating local options, [Llama 3 70B via Ollama](https://ollama.com/) produces solid results and keeps your logs off external servers — a meaningful consideration if you're handling sensitive infrastructure data.

---

## Step 3: Configure Your Data Sources

This is where most of the setup time goes, and where precision matters. Open `config/datasources.yaml`. You'll see annotated sections for each supported integration.

### Prometheus

```yaml
prometheus:
  enabled: true
  url: "http://your-prometheus-host:9090"
  # Optional: basic auth
  auth:
    username: ""
    password: ""
  # How far back to look when building context for an alert
  lookback_minutes: 60
```

Nightwatch only executes PromQL `query` and `query_range` calls — both read-only endpoints in the [Prometheus HTTP API](https://prometheus.io/docs/prometheus/latest/querying/api/). If you're running Prometheus behind an auth proxy, make sure the credentials you supply have no write access to the remote write endpoint.

### Loki

```yaml
loki:
  enabled: true
  url: "http://your-loki-host:3100"
  default_labels:
    app: ""
    env: "production"
  lookback_minutes: 30
```

[Grafana Loki](https://grafana.com/oss/loki/) is queried via its standard LogQL query API. Again, no push endpoints are used.

### Kubernetes

```yaml
kubernetes:
  enabled: true
  kubeconfig_path: "/etc/nightwatch/kubeconfig"
  namespaces:
    - "default"
    - "production"
    - "staging"
```

Create a dedicated kubeconfig for Nightwatch with a service account that has only `get`, `list`, and `watch` verbs. Here's a minimal ClusterRole:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: nightwatch-readonly
rules:
  - apiGroups: [""]
    resources: ["pods", "events", "nodes", "services", "endpoints"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets", "statefulsets", "daemonsets"]
    verbs: ["get", "list", "watch"]
```

Bind this role to a service account and export its kubeconfig. This is the right way to enforce the principle of least privilege, and it pairs perfectly with Nightwatch's read-only guarantees.

## Step 4: Configure Alert Ingestion

Nightwatch can receive alerts from Alertmanager via webhook, or it can be configured to poll your Prometheus alert state on a schedule.

### Webhook mode (recommended for real-time incident response)

In your Alertmanager config, add a receiver:

```yaml
receivers:
  - name: nightwatch
    webhook_configs:
      - url: "http://nightwatch-host:8080/webhook/alertmanager"
        send_resolved: true
```

When an alert fires, Alertmanager will POST the payload to Nightwatch, which immediately begins gathering context from your configured data sources and generating an incident analysis.

### Polling mode

If you can't modify your Alertmanager config, set `polling.enabled: true` in `config/nightwatch.yaml` and specify an interval. Polling is slightly less real-time but requires zero changes to your existing alert pipeline.

## Step 5: Launch With Docker Compose

With configuration files in place, start everything up:

```bash
docker compose up -d
```

Check the logs to confirm the agent initialized cleanly:

```bash
docker compose logs -f nightwatch
```

You should see output like:

```
INFO  Nightwatch starting up...
INFO  LLM provider: openai (gpt-4o)
INFO  Data sources: prometheus ✓  loki ✓  kubernetes ✓
INFO  Webhook listener active on :8080
INFO  Ready.
```

If any data source shows ✗, check your credentials and network connectivity before proceeding.

## Step 6: Review a Generated Incident Report

Once an alert fires (or you trigger a test webhook), Nightwatch produces a structured report. Reports are surfaced via:

- **The web UI** at `http://localhost:3000` (included in the Docker Compose stack)
- **Slack notifications** if you configure the Slack integration in `config/notifications.yaml`
- **Filesystem output** in `./reports/` as JSON and Markdown files

A typical report contains:

| Section | What It Contains |
|---|---|
| **Incident Summary** | Plain-language description of what fired and what the likely blast radius is |
| **Timeline** | Chronological reconstruction of metric anomalies and log events leading up to the alert |
| **Correlated Signals** | Other metrics or logs that changed in the same window, ranked by relevance |
| **Kubernetes Context** | Pod restarts, OOMKills, pending events, recent deploys in the affected namespace |
| **Hypothesis** | The LLM's best-guess root cause, with confidence level and supporting evidence |
| **Suggested Next Steps** | Human-readable checklist of things to investigate — not automated actions |

The "Suggested Next Steps" section is particularly useful at 3 AM. It won't fix your service, but it will hand you a prioritized list of exactly where to look first.

|---|---|---|---|---|---|
| **Nightwatch** | ✅ | ✅ (by design) | ✅ | ✅ | ❌ (intentional) |
| PagerDuty AIOps | ❌ | Partial | ✅ | ❌ | ✅ |
| Datadog Watchdog | ❌ | ✅ | Limited | ❌ | ❌ |
| Robusta | ✅ | ❌ | Partial | ✅ | ✅ |
| Coroot | ✅ | ✅ | Limited | ✅ | ❌ |

Nightwatch occupies a specific, deliberate niche: fully open-source, fully self-hostable, with LLM-quality reasoning and zero write access. If you want autonomous remediation, [Robusta](https://home.robusta.dev/) is the most mature open-source option in that category. If you want enterprise AIOps with deep integrations, PagerDuty is the incumbent. But if your priority is insight without risk — especially in compliance-sensitive environments — Nightwatch has no direct equivalent.

## Tips for Getting the Most Out of Nightwatch

**Tune your lookback windows.** The default 60-minute lookback for Prometheus works for slow-burn incidents, but if your services tend to degrade and recover quickly, drop it to 20–30 minutes to avoid the LLM reasoning over irrelevant historical data.

**Label your alerts richly.** Nightwatch uses Alertmanager labels to scope its Kubernetes and Loki queries. An alert with `namespace="production"` and `app="checkout-service"` will produce a much more targeted report than an alert with only a numeric host IP.

**Consider running a local LLM for sensitive environments.** If your logs contain PII, credentials, or regulated data, routing them through a third-party LLM API is a compliance risk. The [Ollama](https://ollama.com/) integration lets you keep everything on-premise. Expect slightly longer analysis times but full data sovereignty.

**Use the Slack integration.** Even if you're skeptical of chatops, getting the incident report as a thread in your existing incident channel — right next to the PagerDuty page — dramatically reduces the context-switching cost of early triage.

If your on-call rotation involves the ritual of opening five browser tabs, grepping through logs, and trying to mentally correlate a metric spike with a deployment that happened 40 minutes ago — Nightwatch is worth deploying this week. The setup time from zero to first incident report is under an hour for most teams with existing Prometheus/Loki infrastructure.

The trade-off is that it won't fix anything for you — but it will make sure you always know what to fix first.
